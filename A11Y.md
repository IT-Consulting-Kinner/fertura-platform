# Barrierefreiheit (A11y) — Konvention & Checkliste

Ziel: **WCAG 2.1 AA** für alle vom Core und von Modulen ausgelieferten Oberflächen.
Dieses Dokument hält fest, was der Core **bereits systematisch** löst (damit Module
es erben) und liefert die **Checkliste**, die jeder neue Screen (Core *und* Modul)
erfüllen muss.

---

## 1. Was der Core systematisch bereitstellt (erben, nicht neu bauen)

| Belang | Wo gelöst | Effekt für Module |
| --- | --- | --- |
| Sprache | `<html lang>` im Layout | Screenreader-Aussprache korrekt |
| Skip-Link | `layout/admin.php` / `layout/default.php` → „Skip to main content" | Tastatur springt zum Inhalt |
| Landmarks | `<main id="main">`, `<nav aria-label=…>` für Haupt-/Admin-Navigation | Strukturierte Navigation |
| Aktiver Navigationspunkt | `aria-current="page"` | Orientierung |
| Flash-Meldungen | `aria-live="polite"`-Region um Flashes | Statusänderungen werden angesagt |
| Sichtbarer Fokus | `:focus-visible`-Stil im Core-CSS | Tastaturbedienung sichtbar |
| Tabellen (UiKit) | `UiKit->table()`/`sortHeader()`: `scope="col"`, `aria-sort`, Select-all mit `aria-label` | A11y „for free" bei UiKit-Tabellen |
| Pagination | `<nav aria-label="Pagination">` | Als Navigation erkennbar |
| Formulare | CakePHP-`FormHelper`: `<label for>`+`id`, bei Fehlern `aria-invalid`/`aria-describedby` automatisch | Label- und Fehlerkopplung „for free" |
| Handgebaute Tabellen (Core-Admin) | alle `<thead>`-`<th>` mit `scope="col"` | Konsistenz, auch außerhalb UiKit |

**Regel #1:** Für Listen/Detail/Formular **das UiKit benutzen** (`$this->UiKit`). Dann sind
Tabellensemantik, Sortier-ARIA, Select-all-Label und Buttons bereits konform.

**Regel #2:** Für Formulare **den CakePHP-`FormHelper`** (`$this->Form->control(...)`)
benutzen — Label/Feld-Kopplung und Fehler-ARIA entstehen automatisch. Kein
hand­gebautes `<input>` ohne zugehöriges `<label for>`.

---

## 2. Checkliste je Screen (Core & Modul)

Vor dem Merge eines neuen/angepassten Templates abhaken:

### Struktur & Navigation
- [ ] Genau **eine `<h1>`** pro Seite; Überschriften lückenlos verschachtelt (`h1→h2→h3`, kein Sprung).
- [ ] Inhalt liegt in der `<main>`-Landmark (vom Layout gestellt — kein zweites `<main>`).
- [ ] Eigene Navigationsblöcke haben ein `aria-label`.

### Formulare
- [ ] Jedes Eingabefeld hat ein sichtbares, gekoppeltes Label (FormHelper erledigt das).
- [ ] Pflichtfelder sind als solche ausgezeichnet (`required` + visuelle Kennzeichnung).
- [ ] Fehler werden am Feld angezeigt **und** programmatisch gekoppelt (`aria-invalid`/`aria-describedby` — FormHelper-Default; bei Handbau selbst setzen).
- [ ] Zusammengehörige Felder (Radiogruppen) in `<fieldset>` + `<legend>`.
- [ ] Buttons/Submit haben einen aussagekräftigen, sichtbaren Text.

### Tabellen
- [ ] UiKit-Tabelle verwendet **oder** jede Kopfzelle trägt `scope="col"` (Zeilenköpfe `scope="row"`).
- [ ] Datentabelle hat eine `<caption>` *oder* eine zugängliche Überschrift davor.
- [ ] Sortierbare Köpfe tragen `aria-sort` (UiKit-`sortHeader` erledigt das).
- [ ] Select-all-Checkbox hat ein `aria-label`.

### Nicht-Text-Inhalte & Steuerungen
- [ ] Bilder haben `alt` (leeres `alt=""` für rein dekorative).
- [ ] Icon-only-Buttons/Links haben einen `aria-label` **oder** visuell verstecktes Textlabel.
- [ ] Links haben aussagekräftigen Text (kein nacktes „hier"/„mehr").

### Interaktion & Wahrnehmung
- [ ] Vollständig per **Tastatur** bedienbar; Fokusreihenfolge logisch; keine Fokusfallen.
- [ ] Fokus ist **sichtbar** (Core-`:focus-visible` nicht überschreiben).
- [ ] Statusmeldungen erscheinen in einer `aria-live`-Region (Flash-Region des Layouts nutzen).
- [ ] **Kontrast** ≥ 4.5:1 (Text) bzw. 3:1 (große Schrift/UI-Komponenten).
- [ ] Information nie **allein** über Farbe (Status zusätzlich per Text/Symbol).
- [ ] Keine reine Maus-/Hover-Interaktion ohne Tastatur-Äquivalent.

---

## 3. Verifikation
- Render-Tests prüfen die Kern-ARIA: `TenantsControllerTest` (Skip-Link, `id="main"`,
  `aria-current`, `scope="col"` — UiKit **und** handgebaute Tabelle via `/admin/config`),
  `UiKitHelperTest` (Tabellensemantik/Select-all-Label).
- Neue Screens fügen mindestens eine Assertion für ihre A11y-kritischen Knoten hinzu
  (Label-Kopplung, `scope`, `aria-label` der Steuerungen).
- Manuell stichprobenartig: Tab-Durchlauf der Seite + Kontrastprüfung neuer Farben.

*Hinweis:* Vollständige AA-Konformität (alle Modul-Screens, alle Kontraste, alle
Tastatur-Flows) ist ein **fortlaufendes** Thema. Diese Liste ist das verbindliche
Minimum pro Screen; der Core stellt die Bausteine, damit das Abhaken günstig bleibt.
